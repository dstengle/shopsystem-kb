# kb Design

Date: 2026-09-23
Status: Draft for review

## Purpose

kb is a schema-typed, graph-oriented artifact store. It holds typed
documents whose parts are addressable nodes, validates every write against
schemas that are themselves stored artifacts, keeps a git repository as the
canonical serialization, and exposes one versioned API contract that an
in-process client uses today and a network server can host later.

kb knows nothing about any domain. It ships no schemas beyond the
metaschema and no renderers. A client such as shop-knowledge supplies the
types, the seed content, and every presentation of the data.

kb replaces the shopsystem artifact model analysed in
`artifact-model-analysis-2026-09-21.md` and implements the knowledge-base
decisions of `next-system-design-2026-09-22.md`, both in the
shopsystem-product repository.

## Constraints carried from the design note

- Git is canonical. The API is the only access path. The store is derived.
- Every change goes through the API: validate, write, journal, serialize,
  commit. Nothing else edits the serialized text.
- Artifacts are typed, ordered documents. Domain parts are typed nodes with
  ids, never text quoted inside a code fence. Inline formatting is never
  modelled; a prose body is one markdown string.
- Renderings are outputs written elsewhere, never stored in their source.
- Every artifact carries the schema version it was validated against.
  Migration is not built; versioning is.
- The boundary is enforced mechanically: a corpus-only role gets the client
  and no shell; a shell-bearing role runs where the repository is not.

## Decisions taken in this design

| Decision | Choice |
|---|---|
| Serialization | YAML, standard parser, canonical emission by kb only |
| Primary model | A graph whose serialization is documents: one file per artifact, parts inline with ids, references as a schema primitive |
| Shared parts | Their own artifacts, referenced with bindings by the using artifact; a domain concern on top of references |
| Version semantics | Float: one current corpus. Executions snapshot what they read through the journal |
| Extensibility | Types are data. Anything behavioural about a type is client code |
| Validation engine | python-jsonschema with the `referencing` library, extended with kb keywords |
| Runtime shape | Core as a library behind a protobuf contract; in-process transport first; server later |
| Scale | One repository; incremental load cache; batch operations; daemon only when measured |
| Contract stability | The API is the stable boundary. Storage, including git-first, may change behind it |

## What use will tell us

Each is a belief that only use can prove wrong. None is tested by a
scenario or ordered by a slice; they are what the shop's measurement loop
should watch once the system runs.

- **one-current-corpus.** A single floating corpus plus execution
  snapshots is enough reproducibility. Fails if an execution's behaviour
  cannot be explained from its snapshot.
- **summary-is-enough-to-navigate.** A summary read, with stubs of what an
  artifact points at and counts of what points at it, lets a client move
  through the graph without whole reads. Fails if clients routinely follow a
  summary with a whole read of the same artifact.
- **section-reads-are-the-common-read.** Agents load one section at a time.
  Fails if section reads are rare and whole reads are the norm.
- **typed-refs-cover-the-questions.** List, follow-links, and search answer
  what clients ask. Fails if a question needs a traversal the contract
  cannot express.
- **every-fault-at-once-shortens-the-loop.** Returning every violation of a
  write reduces retries. Fails if callers fix one fault per attempt anyway.
- **a-refused-write-changes-nothing.** Validate-then-swap means a rejected
  write, single or batched, leaves the store as it was. Fails if any
  rejected write is observable afterwards.
- **refuse-is-enough-for-deletes.** Refusing a delete that something points
  at, and naming what blocks it, is workable. Fails if operators need
  cascade or detach.
- **stale-is-safe.** An artifact behind its schema's version can be read and
  written without harm until someone updates it. Fails if a stale artifact
  causes wrong behaviour.
- **types-as-data-suffice.** A client can add a type through the contract
  alone. Fails if a new type needs a change to kb.
- **composition-covers-common-fields.** `allOf` with `$ref` is enough sharing
  between schemas. Fails if a type needs to override or mix in.
- **a-use-holds-its-own-settings.** A shared part plus bindings on each use
  covers reuse. Fails if a use needs state the bindings cannot carry.
- **every-change-is-attributable.** Actor, execution, message, and a
  fingerprint per operation are what history needs. Fails if a question
  about how the store got here cannot be answered from the journal.
- **batch-keeps-throughput-adequate.** Batched writes under one lock keep up
  with work tracking without a daemon. Fails if the lock queue grows.
- **git-serves-time-travel.** No historical read in the contract. Fails if a
  client needs a past state through the contract.

## Artifact model

**Nodes.** An artifact is a root node. A part is a node inside an artifact.
Parts nest. Every node is addressable by a path from the artifact root,
such as `steps/draft/branches/0` or `sections/purpose/sections/rationale`.

**Identity keys**, always first in an artifact and never accepted from
input except `title`:

| key | meaning |
|---|---|
| `id` | `<type>/<slug>`, minted by kb from the title on create and never supplied by the client. On collision kb appends `-2`, `-3`, and so on. Stable for the artifact's life; the file path derives from it. The client reads it from the `Create` response. |
| `type` | The id of the schema artifact, without the `schema/` prefix. |
| `schema_version` | Integer version of the schema the artifact was last validated against. |
| `revision` | Integer incremented by kb on every write. |
| `title` | Display name. Changing it is not a rename of anything. |

Changing an id is unsupported until migration exists. A schema change
that would make existing artifacts invalid needs the migration design;
until then `Validate` reports it and nothing prevents it.

**Fields.** Typed values declared by the schema. A reference is a field
type: a string `decision/adr-0007` or, into a part, `process/x#steps/draft`.
The schema declares target types, cardinality, whether part paths are
allowed, and the delete rule. The only delete rule in this version is
`refuse`.

**Sections.** Ordered prose. A section is a `title`, a markdown `body`, and
an ordered list of child `sections`. Heading level is depth: the artifact
title is level 1, top-level sections level 2. The schema's `sections`
keyword is a tree of required titles in order; additional sections may
follow the required ones at any level.

**Parts.** The schema declares part collections. Each item carries an `id`
unique within its collection, first in key order, minted by kb and never
supplied by the client: from the item's `title` when the item schema has
one, otherwise from the item's position, with the same collision suffix as
artifacts. An id is minted once and never recomputed: removing or reordering
items does not rename the others. `Append` returns it. On a `Write` of a
collection, an item carrying an id is the existing item of that id, moved or
changed in place; an item without one is new and is minted an id. An id that
names no existing item is refused. Items have fields per the item schema, which
may itself declare nested collections.

**Rule for what is a part and what is an artifact.** A thing used from more
than one artifact, or that changes independently of its container, is an
artifact. State that belongs to a use of a thing lives on the artifact
representing the use, never on the thing.

## Schema language

A schema is an artifact of type `schema` whose body is a JSON Schema
(Draft 2020-12) document in YAML, validated by python-jsonschema, plus
five keywords the library ignores and kb enforces:

| keyword | where | meaning |
|---|---|---|
| `ref` | on a string or array field | `{ targets: [type...], cardinality: one|many, parts: bool, on_delete: refuse }` |
| `parts` | at artifact or part level | `{ <collection>: { items: <schema> } }`, items get an `id` |
| `sections` | at artifact level | ordered tree of required section titles |
| `summary` | at artifact level | fields shown in a stub besides `id`, `type`, `title` |
| `title` | at artifact level | human name of the type |

Cross-schema `$ref` resolves through the `referencing` library against a
registry of every `schema/*` artifact in the corpus, using URIs of the form
`kb:schema/<type>#/...`. This is how shared data types between schemas are
expressed.

**Common fields by composition.** JSON Schema has no inheritance; kb uses
its composition idiom. A schema that shares fields with others is written as
`allOf: [{ $ref: kb:schema/<base> }, { ...its own fields }]`. The validator
handles the JSON Schema side natively. kb's five keywords compose through
`allOf` and `$ref` as well: reference fields are collected from every
composed schema, the required section tree is the base's tree followed by
the type's, and `parts` and `summary` merge the same way, base first. A
type hierarchy derived from these references, and listing by a base type,
are not in this version.

A metaschema, shipped in kb's code and written to `schema/schema.yaml` on
init, validates schema artifacts. Every schema carries an integer `version`
that increments when it changes. An artifact whose `schema_version` is
behind its schema is reported as stale on load, never failed.

## Serialization

**Layout.** The store is the directory `<root>/kb/`, marked by
`<root>/kb/store.yaml`, which records the contract version, and `<root>/kb/`
is itself the git repository kb owns. Nothing else in `<root>` is the
store's concern. Inside the store: `<type>/<slug>.yaml`, one file per
artifact; schemas at `schema/<type>.yaml`; the journal at
`journal/<YYYY>/<MM>/<DD>/<timestamp>-<seq>.yaml`, one file per entry; a
lock file `.kb.lock`. The incremental cache lives beside the store, outside
the repository, and is never committed.

**Canonical form.** Identity keys first in the order above, then fields in
schema order, then `sections`, then part collections in schema order. Every
prose body is a literal block scalar, however short. Two-space indent,
sequences indented under their key, no line folding at any width, no flow
style, no comments, no anchors, no tags. The same tree always serializes to
the same bytes. Loading uses a standard YAML 1.2 parser; kb never
needs round-trip preservation because it is the only writer.

**Journal entry.** `id`, `at`, `actor: { role, execution }`, `op`,
`artifact`, `path`, `revision`, `schema_version`, `digest` (sha256 of the
canonical bytes after the write), `message`, and `batch`: the id of the
`Apply` that wrote it, or the entry's own id for a single operation, so the
journal alone shows what landed together. Snapshot entries carry
`op: snapshot` and a list of `{ artifact, revision, digest }`. The commit
hash is not stored; the entry is inside the commit and `git log` joins them.

**Renderings are never in this tree.**

## The contract

`kb.proto` defines `service Kb`. The identity keys `id`, `type`,
`schema_version`, `revision`, and `title` are typed fields of the messages
that carry an artifact. `content` is canonical YAML text holding only what
the schema defines: fields, sections, and parts. Content that carries an
identity key is refused as a violation naming the key, so identity is never
open to interpretation on either side. `Create` takes `type`, `title`, and
`content`. Content shape is schema-defined at runtime, and text
preserves key order and number types where a `Struct` would not. Clients
parse it with any YAML parser. The contract file carries a version;
clients pin it.

| rpc | request | response |
|---|---|---|
| `Create` | type, title, content, actor, message | id, revision. Refused without a title, or when content carries an identity key |
| `Read` | locator, level (`summary`, `section` with title, `whole`), resolve depth | node content; on summary, stubs for reference targets and parts, and inbound counts by type and field. Refused with a fault naming the id when the store does not hold it |
| `Write` | locator, content, actor, message | revision |
| `Append` | locator of a collection, item content, actor, message | item id, revision |
| `Delete` | locator, actor, message | revision, or the list of inbound references that block it |
| `Apply` | ordered list of Create/Write/Append/Delete, actor, message | batch id, minted by kb; per-operation results; one commit |
| `List` | type, field filters, output form (`stubs` or `ids`) | matches |
| `Refs` | locator, direction, optional via-field, optional type, depth | stubs with the path taken |
| `Search` | text, optional type, scope (`sections`, `fields`, `all`) | stubs with matching section title and snippet, ranked |
| `Journal` | filters: artifact, actor, execution, batch, since | entries |
| `Snapshot` | execution id, artifact ids | journal entry id |
| `Validate` | nothing | every violation as artifact, path, message; stale artifacts listed |
| `Init` | root path, actor | nothing; creates the store as the subdirectory `kb/` of the root and writes the metaschema there, journalled under the actor with the message "initialise store". Refused when `kb/` already exists under the root, or when the root is inside a store |

Errors are a typed list of `{ artifact, path, rule, message }`. Every
mutating rpc returns all errors found, not the first.

A locator is `{ id, path }` with `path` empty for the artifact root.

**Resolution.** Resolve depth 0, the default, returns references as ids.
Depth 1 inlines each direct reference target in place of its id; depth n
follows references n hops. A target already inlined on the current
resolution path is returned as a reference, not inlined again, so a cycle
terminates. Branches inside a process point at steps of the same process
by id and are not references; resolution does not follow them.

**Finding the store.** A client or the admin CLI finds the store the way
git finds a repository: from the working directory upward until a
directory holding `kb/store.yaml` is met, or `KB_ROOT` names one
explicitly. Neither found, the call is refused and says so; nothing is
guessed.

**Transports.** In-process: a client object with the stub's signature that
calls the servicer directly. Network: `grpc.server` hosting the same
servicer. Switching is a constructor argument on the client.

## Input safety

Everything a client sends is checked before it touches the tree or the disk:

- An id matches `<type>/<slug>` where `type` is an existing schema and
  `slug` is `[a-z0-9]+(-[a-z0-9]+)*`. A part path is a sequence of node
  names of the same alphabet, or a collection name followed by an item id.
  Anything else, including `.`, `..`, `/` in a segment, or an absolute
  path, is refused as a fault; no file is resolved from it.
- A slug is minted from a title by lowercasing, replacing runs of anything
  outside `[a-z0-9]` with one hyphen, and trimming hyphens. A title that
  yields nothing is refused. Titles are strings: content is parsed as YAML
  1.2 and a title is coerced to text, so "2026-09-24" and "yes" are titles,
  not a date and a bool.
- Content is parsed as YAML 1.2 with a safe loader: no tags, no anchors
  resolving to code, no documents beyond the first. A section has exactly
  `title`, `body`, and `sections`; any other key is a violation.
- A file is written only at the path derived from a validated id, inside
  `<root>/kb/`.

## Write path

The invariant: apply to a copy, validate the copy against the corpus, swap
in only on success. The CLI gets this free because its corpus is rebuilt
per invocation; a long-lived process must copy explicitly.

1. Take the lock, with a timeout.
2. Load: parse files whose content hash differs from the cache, rebuild the
   reference index (both directions, from `ref` fields), rebuild the search
   index. Validate every artifact against its schema's current version. An
   artifact behind that version which still fits is reported stale; one
   that does not is reported stale and in violation. Nothing fails.
3. Apply each operation to a copy of the touched artifact.
4. Validate each touched artifact: JSON Schema, then kb keywords with the
   graph in hand. References must resolve to a node of a permitted type.
   Part ids must be unique per collection. Required sections must be present
   in order. Deletes must have no inbound references to the node or
   anything beneath it. Collect every error; if any, stop here.
5. Bump `revision`, set `schema_version` to current (a write to a stale
   artifact validates against the current version; passing, it clears the
   staleness; failing, it is refused like any invalid write), serialize
   canonically to a temp file, rename into place. Write one journal file per
   operation.
6. `git add` every written file by name, one commit, message from the
   request, author from the actor. On git failure restore the files from
   HEAD and report. (No scenario pins the restore; it is revisited if a
   failure ever leaves a stray file.)
7. Update the cache. Release the lock.

Readers do not lock. Per-file writes are atomic through rename.

## Storage is replaceable

Everything under "Serialization" and "Write path" sits behind the contract
and may change. Git-first, the file layout, the cache, and the lock are
implementation. A client that only uses the contract is unaffected by any
of it changing.

## Admin CLI

`kb init <root>`, `kb validate`, and later `kb serve`. No user-facing
operations; those belong to clients.

## Not in this version

- Renderers of any kind, including a markdown projection.
- Domain schemas and seed content.
- MCP or any other presentation of the contract.
- Migration between schema versions.
- Reading historical states through the contract; `git` serves that.
- More than one repository root per store.
- Delete rules other than refuse.
- A daemon.

## Order of building

kb and shop-knowledge are one effort until the walking skeleton is green,
then two.

1. Feature files for both are formulated in one session from both specs
   and committed to the repo whose behaviour they describe. Every kb
   scenario cites the shop-knowledge scenario that needs it; a kb scenario
   nothing upstream needs is a question for the spec, not a feature.
2. One living plan, kept in shop-knowledge, covers both repos until slice
   1 is green: create a decision and read it back through `shop-knol`,
   which needs `Init`, `Create`, and summary `Read` here. The repos are
   checked out side by side and shop-knowledge installs kb as an editable
   path dependency. Slices in this phase may touch both repos and say which
   repo each scenario runs in.
3. When slice 1 is green, the messages it needed are the contract's first
   version. kb is tagged 0.1, shop-knowledge pins it, and from then each
   repo has its own plan. shop-knowledge's scenarios remain the demand
   signal for kb, arriving as a request to bump the contract version.

## Testing

kb is built with the shopsystem-bdd workflow. Feature files are formulated
from this spec, from the perspective of a client of the contract and, for
the admin CLI, of the operator, and implemented red-green against the
in-process transport. Batch is a
scenario. Incremental load is not observable through the contract and is
measured, not specified.
