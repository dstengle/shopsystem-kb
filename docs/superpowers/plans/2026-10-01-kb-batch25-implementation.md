# kb batch 25 Implementation Plan: contract v1

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** kb's public contract becomes v1 (note 2): one method per action in the spec's words, one signature, result or refusal, sets one kind of change with keys, an expected revision on a change, a store started off the wire, package `kb.v1`.

**Architecture:** the servicer stays the one rpc adapter inside the one fail-closed wrapper; requests convert in `requests.py` from `values.py` and `signatures.py`; the domain is unchanged except where a task says. Steps reach the contract through `tests/calls.py`'s helpers wherever they can, so a later reshaping changes one helper.

**Tech Stack:** Python 3.11, protobuf (generated by `make contract`), pytest-bdd.

**Spec:** `spec/` (contract v1 committed 0c2e7b0; `spec/decisions.md` decision/contract-v1 and the entries after it); note `docs/superpowers/specs/2026-10-01-kb-contract-v1-design.md`.

## Decisions: the v1 messages (package `kb.v1`, service `Kb`)

Small values shared by many messages: `Signature { role, execution, message }`; `Locator { id, place }`; `Fault { artifact, place, rule, message }`; `Refusal { repeated Fault faults }`; `Stub { field, id, kind, title, fields }`; `PartStub { collection, id, title }`; `InboundCount { kind, field, count }`; `Hop`, `Reached`, `Match`, `Stale`, `Entry` (with `place` for path; `actor` stays `{ role, execution }` as the history's record), `Snapshotted` as today.

Every response is `oneof outcome { <Result> result = 1; Refusal refusal = 2; }`, the result message named in the right column.

| rpc | request carries | result |
|---|---|---|
| `Create` | `kind`, `title`, `content`, `signature` | `Created { id, revision }` |
| `Replace` | `locator`, `content`, `signature`, `revision` (0 = none said) | `Replaced { revision }` |
| `Add` | `locator` (its place is the collection), `content`, `signature`, `revision` | `Added { id, revision }` |
| `Remove` | `locator`, `signature`, `revision` | `Removed { revision }` |
| `CreateMany` | `repeated CreateItem { kind, title, content, key }`, `signature` | `CreatedMany { batch, repeated Created results }` |
| `ReplaceMany` | `repeated ReplaceItem { locator, content, revision }`, `signature` | `ReplacedMany { batch, repeated Replaced results }` (each with its id) |
| `AddMany` | `repeated AddItem { locator, content, revision }`, `signature` | `AddedMany { batch, repeated Added results }` |
| `RemoveMany` | `repeated RemoveItem { locator, revision }`, `signature` | `RemovedMany { batch, repeated Removed results }` |
| `Read` | `locator`, `oneof level { Summary summary; Whole whole (depth); Section section (title) }` | `Artifact { id, kind, schema_version, revision, title, content, references, parts, inbound }` |
| `List` | `kind`, `fields`, `form` | `Listed { stubs, ids }` |
| `Follow` | `locator`, `depth`, `direction`, `via`, `kind` | `Followed { reached }` |
| `Search` | `text`, `kind`, `scope` | `Found { matches }` |
| `History` | `artifact`, `role`, `execution`, `since`, `batch` | `Entries { entries }` |
| `Snapshot` | `signature`, `artifacts` | `Recorded { entry }` |
| `Check` | nothing | `Checked { violations, stale }` |

The results of a *Many carry ids (`Replaced`, `Removed` and `Added` gain `id` so each result says which artifact it is). A key reference is a link value written `@<key>`; a key is a plain name (the item-name grammar). No `Init`, `Apply`, `Operation`, `Creation`, `Replacement`, `Addition`, `Removal`, `Actor` (as a request field), `Write`, `Append`, `Delete`, `Refs`, `Journal`, `Validate`.

`kb.init(root, role, *, execution="", clock=None) -> None` and `kb.NotStarted(Exception)` with `.faults` live in the package `kb` (`src/kb/__init__.py` re-exports them from the module that owns starting a store); the in-process `kb.client.connect` stays.

## Review Focus

1. A request field never reaches the domain unconverted (rule 2): signatures, keys and expected revisions convert in `requests.py`.
2. A key replaced by a minted name before anything is checked, wherever a link is written (top-level field, inside an item, in a list of links), and a key that names nothing refused with rule `ref`, naming the key.
3. An expected revision compared under the write lock: a change saying one is never re-drafted into landing on a moved artifact (write.land's retry must refuse it with `revision` instead).
4. The published surface pinned by tests so a later change cannot drift it silently.
5. The bench calls v1's methods.

### Task 1: Slice 119 — the changes are Create, Replace, Add and Remove of contract v1

- Check (slice plan): `kb.proto` is package `kb.v1`; the four changes take a `Signature`, answer result or refusal, name kinds `kind` and places `place`; `Write`, `Append`, `Delete` and `Actor` as a request field are gone; a published-contract test pins these messages; `make test` gives the same answer as the baseline (the same failing ids).
- Where: `src/kb/contract/kb.proto` and the generated code; `servicer.py` (method names, responses built as result or refusal — one helper for every rpc); `requests.py` (the conversions); `signatures.py` (a writer's signature from `Signature`); `client.py` if it names methods; `bench/bounds.py`; `tests/calls.py` (helpers `create`, `request`, `write`→`replace`, `append`→`add`, `remove`, returning what steps need) and every step that builds these requests directly (grep `CreateRequest`, `WriteRequest`, `AppendRequest`, `DeleteRequest`, `Actor(`, `.faults` on their responses). Other rpcs keep their v0 shapes in this task but move into package `kb.v1` with the file.
- Decision: a helper in `tests/calls.py` gives steps a uniform view of an outcome (the result, or the faults) so steps that asserted `response.faults` keep their meaning.

### Task 2: Slice 121 — a set is one kind of change, and new artifacts in it point at each other by keys

- Scenarios (13, `-m slice-121`), make-several-changes-in-one-go.
- Why red: there is no `CreateMany`; `Apply` mixes kinds; no key is read; several rewritten scenarios are bound by their old titles (rebind them; the guard test requires every title bound once).
- Where: proto (`CreateMany`, `ReplaceMany`, `AddMany`, `RemoveMany`; `Apply` and its operation messages removed); `servicer.py`; `requests.py` (each item converted, keys checked: a plain name, unique in the set — a duplicate is rule `ref` naming the key); the domain: a new module or `drafting.py`/`edits.py` puts each minted name in place of `@<key>` before the set is checked (`names.py` decides what a key looks like, rule 6); a key no create carries, or a key with a place (`@key#…`), is refused with rule `ref` naming the key or the reference. The import path keeps its own operations (it is not on the contract).
- Decision: keys exist only in `CreateMany`; an `@` link in a single `Create`, or in a `ReplaceMany`, is an ordinary link value (and so lands on nothing).

### Task 3: Slice 122 — a change may say the revision it read, and is refused if the artifact moved since

- Scenarios (17, `-m slice-122`), change-the-store and make-several-changes-in-one-go.
- Why red: no request carries a revision to compare; rule `revision` does not exist (the rule-names test fails on it).
- Where: `rules.py` gains `revision`; `requests.py` converts the expected revision (0 = none); the domain compares it with the artifact's revision as the set's earlier changes left it, and `write.land` refuses with `revision` (naming the revision it stands at, nothing written) when a change that says one meets a `Conflict` — never re-drafts it into landing; the draft under the write lock compares again.
- Steps: "the client read the decision at its first version" and "another client has since replaced the decision" reuse the existing two-client steps where possible.
